## 4.3 可接受的顶层设计概念方向

以下设计概念方向是**可由现有知识库支持的**：

### Concept A: Layered / Separated Responsibilities
将系统划分为若干高层职责区：
- 前端交互
- 接口接入
- 业务处理
- 外部集成
- 运维支撑

**可推导依据：**
- QA-6 要求接口变化不影响核心
- QA-9 要求外部依赖隔离
- CRN-3 要求可分工
- CRN-4 要求避免技术债

### Concept B: Separate Query and Change Responsibilities
把“价格查询”和“价格变更/发布”视为不同职责区域。

**可推导依据：**
- HPS-2 与 HPS-3 是不同主路径
- QA-1/2/8 与 QA-3/4/6 驱动力不同
- 查询强调可用性/扩展性
- 变更强调性能/可靠发布/监控

### Concept C: Explicit External Integration Boundary
对以下外部交互设置明确边界元素：
- User Identity Service
- Channel Management System
- External query callers

**可推导依据：**
- HPS-1、HPS-2、HPS-3、QA-5、QA-2、QA-9

### Concept D: Event-oriented publication support using Kafka
若 DesignAgent 选择 Kafka 支撑价格发布链路，这是**可接受的**，因为：
- CRN-2 明示要求 leverage Kafka
- QA-2、QA-8 对发布可靠性和可监控性提出压力

但必须注意：
- 只能说明“选择 Kafka 作为价格发布相关的技术支撑概念”
- **不能擅自声明 Kafka 自动保证 exactly-once、持久化语义、消息顺序等未在知识库中提供的性质**
- 若使用这些性质作为论证，则属于**引入外部知识**，必须修正

### Concept E: Front-end separated from backend responsibilities
采用 Angular 前端与后端职责分离是可接受的。

**依据：**
- CRN-2 明示 Angular
- HPS-1~HPS-6 都存在用户交互需求
- QA-5 涉及前端登录
- QA-7 涉及部署环境迁移

基于 Step 3 已确定的责任方向，本轮只选择能直接支撑“主要功能结构识别”的高层设计概念，不提前落入运行时优化、存储技术或部署拓扑细节。

### 概念 A：分层 + 责任域分解
将 HPS System 按职责划分为若干高层元素：
- 表现/访问入口
- 认证授权
- 定价
- 管理
- 外部集成

**适配驱动：**
- 支撑全部主要功能
- 有利于团队分工（CRN-3）
- 有利于降低耦合，避免技术债（CRN-4）
- 满足整体初始结构建立（CRN-1）

### 概念 B：端口-适配边界（用于外部系统与协议隔离）
对以下变化点建立边界：
- User Identity Service
- Channel Management System
- Price Query API 协议入口

即：核心职责不直接依赖外部系统和具体查询协议，而通过明确接口边界交互。

**适配驱动：**
- **QA-6**：增加非 REST 查询端点时，不改核心组件
- **QA-9**：外部系统可替换/隔离，支持独立集成测试
- **QA-5**：身份校验与权限能力有独立边界

### 概念 C：读写职责分离到服务边界级别
在定价责任域内部，至少在结构上区分：
- **Price Change / Publication path**
- **Price Query path**

注意：这里是职责边界分离，不等于引入额外运行时机制。

**适配驱动：**
- HPS-2 与 HPS-3 是不同交互路径
- **QA-6** 要求查询协议扩展不影响核心
- 后续也为 QA-1/QA-4 留出结构基础

### 概念 D：前端与后端职责分离
采用：
- **Angular Frontend** 负责用户交互
- 后端 API / application elements 负责业务处理

这是对 **CRN-2** 中 Angular 技术已知约束的直接利用。

**适配驱动：**
- HPS-1/2/3/4/5/6 都存在用户交互面
- 有利于职责清晰
- 支持团队分工

1. **分层 + 责任域分解**
2. **端口-适配边界**
3. **定价读写职责分离**

### DD-2-1：将 HPS System 分解为高层责任域元素
**决策**

- CRN-1

- CRN-4

- 本轮目标是识别支持主要功能的结构，因此必须进行高层分解。
- 六个主要功能天然分属不同责任面：访问、认证授权、定价、查询、管理、外部集成。
- 有助于团队按责任域分工。

### DD-2-2：将认证/授权从表现层和业务处理中显式分离
**决策**  
设置独立的 Authentication & Authorization Component。

**来源依据**  
- HPS-1

- QA-9

**理由（Rationale）**

### DD-2-3：在查询入口与查询核心之间保留协议隔离边界
**决策**  
价格查询能力不直接与单一协议实现耦合，需保留入口边界与查询核心的分离。

**来源依据**

## Step 4.1 复核本轮驱动因素

## Step 4.2 针对“价格变更发布链路”的候选设计概念

本轮要解决的核心问题之一是：

- **价格变更必须成功发布并被 Channel Management System 接收**（QA-2）

在不引入外部知识的前提下，可从已知约束中直接导出的候选概念只有以下几类。

### 候选概念 A：同步直连发布
即：

- Price Change 处理服务在处理变更时
- 直接同步调用/推送到 **Channel Management System**
- 以此完成“发布”

#### 优点
- 结构直接
- 责任边界清楚

#### 风险
- QA-2 要求不仅“系统内部完成”，而且“Channel Management System 接收”
- 如果把外部系统调用直接放在主处理链路上，则价格变更处理可靠性会强依赖外部边界
- 同时这类强耦合方案不利于 **CRN-4 避免技术债**
- 也不利于后续稳定演进和团队分工（CRN-3，虽然不是本轮主驱动，但应保持一致）

#### 评审结论
- **不优先选择**

---

### 候选概念 B：基于消息/事件通道的发布链路
即：

- 价格变更完成后，不直接把所有可靠性交互压在同步接口上
- 而是通过一个明确的**消息/事件通道**
- 再由专门的发布元素与 **Channel Management System** 交互

#### 直接推导依据
- **CRN-2 明确给出 Kafka 为团队已知技术**
- Step 3 也已明确：若前序架构中存在消息/事件通道，应纳入细化范围
- QA-2 要求重点在“发布成功并被接收”，因此将“变更处理”和“对外发布”分离，有助于单独细化发布职责边界

#### 优点
- 更符合本轮对可靠性链路进行独立细化的目标
- 便于把“价格变更处理”和“对外发布”拆成不同元素，支持团队分工
- 与 CRN-2 一致
- 相比把外部系统同步耦合进主处理流程，更符合 CRN-4

#### 风险
- 仅有消息通道本身并不能自动证明满足“100%成功并被接收”
- 因此 Step 5 中必须明确：
  - 哪个元素负责发布
  - 哪个元素负责与 Channel Management System 交互
  - 哪个边界承担“已发布可供查询”和“已投递到外部”的职责分离

#### 评审结论
- **选择该概念作为主方案**

---

## Step 4.3 针对“价格查询运行链路”的候选设计概念

本轮第二个核心问题是：

- **价格查询在维护窗口外达到 99.9% uptime SLA**（QA-3）

### 候选概念 C：查询与变更共用同一处理路径/同一核心服务
即：

- 查询请求进入后
- 通过与价格变更相同的核心处理元素和同类依赖完成返回

#### 风险
- Step 3 已指出：查询路径通常需要与变更发布路径区分分析
- 若查询依赖变更发布链路中的同步外部交互，则会直接扩大可用性受影响范围
- 不利于明确可用性边界

#### 评审结论
- **不优先选择**

---

### 候选概念 D：查询路径与变更发布路径分离
即：

- 为 **HPS-3 Query Prices** 提供独立的查询入口元素和查询处理元素
- 查询从“已发布价格”的读取边界获取数据
- 不把 **Channel Management System** 作为查询同步阻塞前提

#### 直接推导依据
- QA-3 约束的是查询可用性
- Step 3 已明确：应细化“查询 API / 查询处理服务 / 已发布价格读取边界”
- Step 3 还明确：需要分析哪些外部依赖不应成为查询路径的同步阻塞点

#### 优点
- 收敛查询可用性受影响的范围
- 支撑独立演进和独立部署边界
- 与后续 QA-6 的“新增不同协议端点不改核心组件”也保持兼容，虽然本轮不以其为主

#### 评审结论
- **选择该概念作为主方案**

---

## Step 4.4 本轮最终采用的设计概念

### 设计概念 1：价格变更处理与价格发布分离
- 由一个应用元素负责接收并处理价格变更
- 处理结果写入“已发布价格”边界
- 同时通过 **Kafka** 将待发布事件交给专门发布元素
- 专门发布元素与 **Channel Management System** 交互

### 设计概念 2：查询路径独立化
- 提供独立的 Query API
- Query Service 只依赖“已发布价格读取边界”
- 查询路径不以 Channel Management System 为同步前提

### 设计概念 3：外部系统交互通过专门边界元素承担
- 将 **Channel Management System** 交互收敛到单独元素
- 避免外部依赖扩散到查询和价格变更入口

**接口**：

## 5.2 元素之间的关系

### 价格变更与发布链路
1. 用户或前端调用 `Price Change API`
2. `Price Change API` 调用 `Price Change Service`
3. `Price Change Service`
   - 计算/准备价格结果
   - 写入 `Published Price Store`
   - 发布事件到 `Kafka Price Publication Topic`
4. `Channel Publication Service` 消费该事件
5. `Channel Publication Service` 调用 `Channel Management System Boundary`

---

### 查询链路
1. 用户或外部系统调用 `Price Query API`
2. `Price Query API` 调用 `Price Query Service`
3. `Price Query Service` 从 `Published Price Store` 读取价格
4. 查询结果返回调用方

## 6.2 设计决策记录（Decision Log）

---

### Decision D3-1：将价格变更处理与对 Channel Management System 的发布职责分离

**决策内容**  
采用两个不同的内部元素承担不同职责：

- `Price Change Service` 负责处理价格变更并写入 `Published Price Store`
- `Channel Publication Service` 负责向 `Channel Management System` 发布

两者之间通过 `Kafka Price Publication Topic` 连接。

**来源依据**
- QA-2 Reliability
- HPS-2 Change Prices
- CRN-2（Kafka）
- Step 3 中已明确：需细化价格发布相关元素与 Channel Management System 的交互边界

**Rationale**
- QA-2 的焦点是“价格变更成功发布并被 Channel Management System 接收”，因此“变更处理”和“对外发布”需要在结构上明确分离，便于单独分析可靠性责任边界。
- CRN-2 明确允许并鼓励利用团队已知的 Kafka。
- 相比将外部系统调用直接嵌入价格变更主处理路径，该方案更符合“细化发布链路”的本轮目标，也更符合 CRN-4“避免技术债”的方向。

**评审说明**
- 这是一个**结构性支持决策**。
- 它说明系统把职责边界划分清楚了。
- 但它**尚不足以单独证明** QA-2 中的“100%成功并被接收”。

---

### Decision D3-2：采用 Kafka 作为价格发布事件通道

**决策内容**  
在 `Price Change Service` 与 `Channel Publication Service` 之间引入 `Kafka Price Publication Topic` 作为消息/事件通道。

**来源依据**
- CRN-2：团队具备 Kafka 知识
- Step 3：若前序架构存在消息/事件通道元素，则其应纳入细化范围
- QA-2：需要重点细化发布链路

**Rationale**
- Kafka 是知识库中明确给出的可利用技术，因此引入它不属于外部扩展。
- 它可将价格变更处理与外部发布边界解耦，使发布责任由专门元素承担。
- 这有利于后续围绕发布链路继续分析可靠性与运行支撑。

**评审说明**
- 该决策是**合规的**，因为 Kafka 的引入有明确约束来源。
- 但不能把“使用 Kafka”自动等同于“满足 100% 可靠性”，否则会构成隐式推断。

---

### Decision D3-3：将查询路径与价格发布路径分离

**决策内容**  
采用独立的查询链路：

- `Price Query API`
- `Price Query Service`
- `Published Price Store`

查询路径不直接依赖 `Channel Management System`。

**来源依据**
- QA-3 Availability
- HPS-3 Query Prices
- Step 3：查询 API、查询处理服务、已发布价格读取边界都应作为细化对象
- Step 3：需明确哪些外部依赖不应成为查询路径的同步阻塞点

**Rationale**
- QA-3 约束的是“定价查询可用性”，因此查询路径必须有独立分析边界。
- 如果查询依赖外部渠道系统，则外部系统故障会直接扩大查询不可用范围，不利于满足 99.9% uptime 的结构支撑。
- 将查询建立在内部“已发布价格”读取边界之上，更有利于维持查询服务边界的稳定性。

**评审说明**
- 这是本轮最直接支撑 QA-3 的结构决策。
- 但同样只能说明“更有利于可用性”，还不能据此直接宣称 SLA 已被证明满足。

---

### Decision D3-4：设置 Published Price Store 作为查询读取边界与价格变更写入边界

**决策内容**  
引入 `Published Price Store`：

- 由 `Price Change Service` 写入
- 由 `Price Query Service` 读取

**来源依据**
- Step 3 明确要求：查询链路至少覆盖“已发布价格的读取边界或数据提供边界”
- HPS-2 / HPS-3：变更后的价格需要能够被查询

**Rationale**
- 若要使查询路径独立于外部发布边界，必须存在一个内部、可供查询使用的数据边界。
- 该元素使“内部可查询价格”与“外部渠道接收价格”两个责任点在结构上分开。

**评审说明**
- 该决策是由 Step 3 明确支持的。
- 命名为 “Published Price Store” 与前文定义一致，没有越界到具体数据库实现。

**评审说明**

- `Channel Publication Service -> Channel Management System Boundary`

#### 不足 2：没有定义异常场景下的处理机制
QA-2 要求 100% 成功，而当前设计未说明：

- Kafka 消费失败怎么办
- 对外发布失败怎么办
- 处理中断怎么办
- 如何保证多次价格变更都成功到达外部系统

注意：我不是要求你现在必须加入某种外部模式；我是在指出：
- **当前设计证据不足**
- 因此不能在 Step 7 中给出“已满足 QA-2”的结论

#### 不足 3：内部“已发布价格”与“外部系统已接收”之间存在状态差异，但未被分析
当前设计中：
- `Published Price Store` 被写入后，查询已可读取
- 但 `Channel Management System` 是否已接收，可能尚未确定

这意味着“内部可查”与“外部已接收”在概念上并不等同。

## 4.2 设计概念候选

### 候选概念 A：将开发运维能力隐含在现有业务组件内部
即：
- 在价格发布相关组件内部直接加入监控逻辑；
- 在业务组件中直接处理环境配置；
- 外部系统调用点不额外抽象；
- 测试时通过直接替换连接配置或条件分支处理。

#### 优点
- 初始结构较少
- 看似实现快

- **QA-9** 风险高：外部系统替换点不明确，不利于独立集成测试

- **CRN-3** 不利：职责边界不清，团队分工困难

### 候选概念 B：采用显式边界分离的结构

1. **外部系统适配边界**
2. **配置/部署支持边界**
3. **监控/运维支撑边界**
4. **价格发布应用路径中的可观测发布职责**

并使业务核心通过清晰接口依赖这些边界元素。

#### 优点
- 直接支持 **QA-9**：外部依赖有明确替换点
- 直接支持 **QA-7**：环境相关配置可与代码分离
- 直接支持 **QA-8**：观测能力可作为明确责任分配
- 支持 **CRN-5**：便于持续部署流程围绕可配置构件建立
- 支持 **CRN-3**：前端、后端业务、集成、运维支撑可并行分工
- 支持 **CRN-4**：降低职责耦合，减少技术债

#### 缺点
- 元素数量增加
- 需要更明确接口定义

### DD-4-1：采用“显式边界分离”的结构，而不是把开发运维职责隐含在业务组件中

**Decision**  
选择将外部集成、配置部署、监控运维等职责显式建模为独立元素，而不是散布在现有业务组件内部。

**Rationale**  
这是由本轮驱动因素直接推出的：
- **QA-7** 需要环境迁移不改代码，因此配置职责不能散落在业务逻辑中。
- **QA-8** 需要价格发布链路 100% 可观测，因此监测职责必须显式存在。
- **QA-9** 需要可脱离外部系统进行集成测试，因此外部依赖必须有清晰替换点。
- **CRN-5** 需要持续部署基础设施，因此部署支撑不能仅作为隐含实现细节。
- **CRN-4** 要避免技术债，显式职责边界比散布式嵌入更可控。
- **CRN-3** 要支持团队分工，显式边界更利于责任划分。

**Implications**  
- 元素数量增加；
- 需要额外定义接口关系；
- 但换来更清晰的测试、部署、监控与团队协作边界。

**Review Verdict**  
该决策**成立**，且推导充分。
