### ✅ **Step 5: Instantiate Architectural Elements, Allocate Responsibilities, and Define Interfaces**  

Per ADD 3.0, we now instantiate the **Cross-Cutting Infrastructure Layer** (selected in Step 3) into three concrete, named elements — each realizing *one* design concept, with *explicit responsibilities*, *well-defined interfaces*, and *strictly UPKB-derived collaborations*.

All names, interfaces, and responsibilities are **logically entailed** — no invention:  
- `ConfigBinder` → from “externalized configuration” + QA-7’s “no code changes” → must *bind* config, not *store* it.  
- `TestSeamRegistry` → from DI pattern + QA-9’s “independently of external systems” → must *register and resolve* substitutable implementations.  
- `TelemetryEmitter` → from Domain Event pattern + QA-8’s “collect 100%” → must *emit* events, not *process* or *store* them.

#### 🔹 Element 1: `ConfigBinder`  
- **Responsibility**: Load and bind environment-specific configuration values (e.g., `channel-management.timeout-ms`, `cache.ttl-seconds`) into typed, immutable configuration objects *at application startup*, without recompilation.  
- **Interface**:  
  ```java
  public interface ConfigBinder<T> {
      T bind(Class<T> configType); // e.g., bind(PricePublicationConfig.class)
  }
  ```  
- **Collaborations**:  
  - Consumed by *all functional services* (e.g., `PriceService`, `UserService`) to obtain their configuration.  
  - *Does not collaborate with `TestSeamRegistry` or `TelemetryEmitter`* — configuration binding is orthogonal to testing/monitoring.  
- **UPKB Trace**: QA-7 (“no code changes”), CRN-5 (“continuous deployment infrastructure” → config must be external to artifact).

#### 🔹 Element 2: `TestSeamRegistry`  
- **Responsibility**: Provide runtime resolution of interface implementations based on active context (e.g., `PROD` vs `INTEGRATION_TEST`), enabling substitution of external collaborators (e.g., `ChannelManagementClient`) without modifying business logic.  
- **Interface**:  
  ```java
  public interface TestSeamRegistry {
      <T> T get(Class<T> contract); // e.g., get(ChannelManagementClient.class)
      void register(Class<?> contract, Object implementation); // for test setup
  }
  ```  
- **Collaborations**:  
  - Functional services use it *only during construction* (e.g., `new PriceService(config, registry.get(ChannelManagementClient.class))`).  
  - *No runtime dependency*: once constructed, services hold direct references — satisfying QA-9’s “independently of external systems” at integration-test time.  
- **UPKB Trace**: QA-9 (“support integration testing independently”), CRN-4 (“avoid technical debt” → no `if (testMode)` branches).

#### 🔹 Element 3: `TelemetryEmitter`  
- **Responsibility**: Emit immutable, schema-validated domain events representing key milestones in the price publication workflow (HPS-2), with mandatory metadata: `eventId`, `correlationId`, `timestamp`, `hotelId`, `dateRange`, `status`.  
- **Interface**:  
  ```java
  public interface TelemetryEmitter {
      void emit(DomainEvent event); // e.g., emit(new PricePublicationSucceeded(...))
  }
  ```  
- **Collaborations**:  
  - Called *synchronously* by `PriceService` at precise points in HPS-2 workflow (e.g., after base rate update, before Channel Management push, on success/failure).
